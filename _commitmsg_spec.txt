The spec named two of our defects: settlement_pending, and the double signature

The owner forwarded the x402 Foundation's github-discussions channel. Two things
in it are ours, and the specification now gives both a name — so they are no
longer a matter of opinion.

1. settlement_pending — WE WERE LOSING PAYING CUSTOMERS
   x402 v2 spec §9 adds `settlement_pending`: "the settlement transaction was
   broadcast but its confirmation could not be established" (an RPC error or a
   timeout waiting for the receipt). The code is NON-TERMINAL — the transaction
   may still confirm — and the response MUST carry the broadcast hash so the
   caller can reconcile on chain.

   We read `success: false` as "the payment failed", so a settlement that HAD
   been broadcast was refused and the paying customer lost their call. The rate
   is not theoretical: Lena Hierzi measured 19 settle 500s in ~11.7k settles on
   a production facilitator, and 9 of them had actually settled.

   Fixed with `_adopt_settlement_pending` in services/connectors.py: the hash is
   adopted and main.py verifies it on chain (a USDC Transfer to our receiver for
   at least the price) before delivering. Matching is on the CODE, never the
   message text — spec §9 requires that, because a facilitator may reword
   errorMessage in any release. Wired into BOTH facilitator paths, not only CDP:
   the code is spec-level, so any facilitator may return it.

   Also adds `_tx_hash_or_none`, one shape check for every place that adopts a
   hash a facilitator named.

   Tests: test_settlement_pending_is_adopted_not_treated_as_a_failure,
   test_settlement_pending_matching_is_on_the_code_not_the_message.

2. OUR npm CLIENT SIGNED AGAIN ON EVERY RETRY — A DOUBLE PAYMENT
   Niraj Vora (issue #3438) describes this exact defect from the buyer side. In
   packages/x402-client/src/index.js, `pay()` was called on EVERY 402 round, and
   each call produces a NEW EIP-3009 authorization with a NEW nonce. A server
   that answered 402 after the first credential had already been broadcast was
   handed a SECOND, independent authorization — the buyer paid twice.

   Against OUR server this was not reachable (we answer 401 or 425, never 402,
   once a credential is presented) — but the package is published on npm for use
   against any x402 server.

   Now: AT MOST ONE SIGNATURE PER REQUEST. A second 402 for terms the client has
   already signed returns `{ error: "payment_outcome_unknown" }` instead of
   signing again. Recovering from there needs an on-chain look at the
   authorization nonce, which this package deliberately does not do (zero
   dependencies, no RPC).

   Version bumped to 1.1.2 (publishing to npm is an external action and awaits
   the owner's go-ahead). Also fixes the stale "~24 seconds" note: the server
   now requires 3 confirmations (~6s), and the wait is server-side.

   Test: "a repeated 402 never buys the same purchase twice" (15/15 in the
   package).

3. NOTED, DELIBERATELY NOT CHANGED: extra.paymentFlow
   Spec §6.1 defines authorization (default), upfront and escrow, and requires
   accepts[].extra.paymentFlow to be present when the flow is not
   authorization. Our Rail 2 (plain transfer + tx-hash claim) is exactly a
   client-prepaid method with an `upfront` flow.

   It is NOT declared in accepts[] on purpose: its transport is our own header
   (X-Payment-Proof), not the standard PAYMENT-SIGNATURE. Advertising an
   accepts[] entry a spec-compliant client cannot pay would mislead the very
   clients the specification exists for. That is an owner decision, not a silent
   change.

Suite advertised count 1389 -> 1391 (README x2, discovery.py).
