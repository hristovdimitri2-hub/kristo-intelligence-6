The CDP status feed cost us nothing — but reading our own tables found a real bug

The owner forwarded the CDP status feed. Its incidents (9-13.11) are exactly the
conditions under which a facilitator answers `settlement_pending`, the code
adopted in the previous commit — so I read the production tables instead of
assuming.

_forensics/did_cdp_incidents_cost_us.py (READ-ONLY, `default_transaction_read_only`).
Last 14 days:

    payment_attempts:  settled 56 | rejected 16 | settle_failed 4

THE ANSWER: CDP cost us nothing. "Degraded Performance — Coinbase Payments" said
explicitly that payments using funds on Base were NOT affected, and our failures
cluster on 09.11 — BEFORE the 10-11.11 incidents. The causes are ours:

    9  payload_undecodable — the client sends a payload we cannot decode
    3  payai_unreachable(status=400) — PayAI rejecting (fixed by _with_accepted)
    2  local_eip712_recovery_failed: Missing value for field `verifyingContract`
    2  20s deadline (verify / settle)

FIXED: THE EIP-712 DOMAIN WAS BUILT FROM THE CLIENT, NOT FROM US

`_local_recover_signer` took `verifyingContract` from the client's `accepted`.
A client that echoed a PARTIAL `accepted` — `scheme` and `network`, which is
perfectly normal — left `verifyingContract` as None and eth_account raised

    ValueError: Missing value for field `verifyingContract` of type `address`

which surfaced as `local_eip712_recovery_failed` and read like OUR bug. It cost
two attempts in production on 09.11.

The domain is now OURS (asset, network, token domain — we issued them in the
402) and the client's values are only a fallback. Same rule as
`_merged_requirements`. It is also the more correct CHECK: a signature made over
a different domain recovers to a different address and fails the `from`
comparison — exactly the rejection we want. When nothing anywhere names an asset,
the refusal is a clean sentence rather than eth_account's raw message.

Test: test_recovery_uses_our_domain_when_the_client_echoes_a_partial_accepted —
covers the full accepted, the partial one, no asset anywhere, and (the important
half) that recovering against a DIFFERENT verifyingContract does not return the
payer.

Noted, not done: `payload_undecodable` (9) is client-side, but the message is too
generic to diagnose from — a candidate for improvement.
