I got the confirmations wrong: Base blocks are 0.2s, not 2s

WHAT I DID WRONG

An earlier commit cut the confirmation depth from 12 to 3, justified by "12
blocks on Base is ~24s, and a 2s block is not a 2s reorg window". The first half
was FALSE. Base produces a block every ~0.2s, so 12 blocks is ~2.4s, not ~24s.

  * 12 was never the cost it looked like — the number had simply been chosen
    under the old cadence;
  * the 3 blocks that replaced it were ~0.6s, not the ~6s I published;
  * I put that wrong figure in ~15 files and pinned it with tests.

HOW IT SURFACED

Not from our code — from a STRANGER'S weekly report. x402 Payability Report 13:
"Base now produces blocks roughly every 0.2 seconds instead of 2. A 7-day window
is 1,260,025 blocks this week. If your tools convert days to block counts at 2
seconds, they already cover about a tenth of the time you think."

Measured it myself rather than believing the post: 25 consecutive blocks around
57,215,802, mean gap 0.21s.

FIXED

  proof rail     3 blocks (0.6s)  ->  12 blocks (~2.4s)
  standard rail  1 block  (0.2s)  ->   5 blocks (~1.0s)

Adds `BASE_BLOCK_SECONDS = 0.2` with the measurement and its date, so the basis
of both numbers travels with them. Every LIVE surface now says "12 confirmations,
about 2.5 seconds" instead of "3 confirmations, about 6 seconds" — 37
replacements across 16 files. Historical entries in HANDOVER.md and
docs/PROJECT_CHRONOLOGY.md are deliberately NOT touched: they record what was
believed at the time, which is the evidence of how the mistake happened.

Why 5 for the standard rail: 1 block was chosen when a block was 2s; at the
measured cadence it is a 200ms window, which is not a guard. A client that
arrives early gets a 425 and re-sends the SAME credential, so the cost of a
deeper wait is a short delay, never a lost sale.

TESTS

tests/test_confirmation_depth.py — four tests that make the arithmetic EXPLICIT:
the cadence must be sub-second, the proof rail must ask for 1.5-5s, the standard
rail must have at least 0.5s, and both must stay inside their published promise.
The next cadence change breaks a test here instead of being found in the wild.

THE LESSON

A block COUNT is not a duration. A guard expressed in blocks silently changes
meaning when the chain changes cadence, and nothing in the code said so. The
number should be stated in TIME, or at minimum have its basis written next to it.

Suite advertised count 1393 -> 1397 (README x2, discovery.py; 4 new tests).
