Kristo Intelligence

Sentient Foundation — Open Source AGI Grant · grant track · supporting document · 20 November 2026

What it is

Seven paid HTTP routes and seven MCP tools on Base, sold to AI agents per call in USDC over x402, MIT-licensed. Every route answers an unpaid request with a real 402 challenge; the buyer pays on-chain and retries. No accounts, no API keys, no signup.

It is also the instrument the findings below were measured on. The project exists as a working endpoint first, and as an argument second.

The problem: both ends of the payment chain report success to the wrong party

1. Delivery end — settlement is non-terminal, and the boolean lies. The x402 v2 spec names settlement_pending: the transaction was broadcast but confirmation could not be established. It is non-terminal, and the response must carry the hash so the seller can reconcile against the chain. We were reading success: false as "this payment failed", so a settlement that had already been broadcast was refused and the paying caller lost the call it had paid for. A facilitator operator in the working group measured ~19 settle failures across ~11.7k settlements, 9 of which had in fact settled.

2. Offer end — the offer that gets published is not the offer that was signed. The catalogue's own transformation is invisible from the seller's side. It appends #toolName to a resource path, so declaring /mcp#get_whale_flow stores /mcp#get_whale_flow#get_whale_flow. An unknown key inside accepts[0] is accepted and silently voids the row: ours were extra_name / extra_version, bookkeeping for our own EIP-712 pre-check. The facilitator settled, we got a hash, and eight settlements produced no listing. Removing the two keys: listed in 45 seconds.

Both ends have the same shape: everything reports success, and the party that believes something happened is not the party that can check it. That is the gap this project is built to close — and the gap the grant would let us close for other sellers too.

What is open, and what would get worse if it closed

  • MIT licence, whole repository. ~98k lines of Python, 651 commits, 1,446 tests, 15 documented OpenAPI paths. The endpoint, the tests and the findings are the same artefact.
  • The settlement_pending conformance cases. The only seller-side cases we know of that treat a broadcast-but-unconfirmed settlement as non-terminal. If the repository closes, the cases close, and the next seller re-learns the lesson by refusing a customer who had already paid.
  • The offer-preview tool. It walks the paid routes, takes each 402, and diffs the declaration against the listing the catalogue intends to publish. First run against the live server: 7/7, no differences. Closed, it becomes a service; open, it is a habit anyone can run before paying.
  • The honest split. The numbers below are published as a split, not a total. A closed project quotes the total.

What we say against our own interest

  • One of the seven endpoints sells a forecast. Its own public track record shows 52% one-sided hits and no measured edge. The other six sell facts a buyer can check. The application leads with the six.
  • Two stars on GitHub. The project is young and the code is not why anyone has found it yet.
  • The revenue is cents. The grant is not a bet on this endpoint's commercial success; it is a bet that the conformance work is worth more than the endpoint's margin.
